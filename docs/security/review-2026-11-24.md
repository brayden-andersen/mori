# Security review, 24 November 2026

**Scope:**
- the live web app (www.morisandbox.com, built from `claude/festive-allen-tw9q27` at `0bf6856`)
- the production Supabase project `ovchugvbujrqkowjalfx`
- the repository and its CI

**Method:**
- code reading
- Supabase's security and performance advisors
- read-only SQL on production: policies, grants, functions, triggers, constraints, buckets,
  settings. No member data was read, and nothing was changed.
- npm audit

**What couldn't be checked from here:** a few dashboard settings, listed at the end.

## Verdict

For an invite-only prototype, the security foundations are solid:

- Every table is behind row-level security, with tight, column-level write rights.
- Sign-up is locked down at the database.
- The browser side has a strict content-security policy and a sanitiser on everything members write.

No issue lets one member read or change another member's data.

The risks that matter most are about **integrity and process**, not about breaking in:

- Edits can look saved when they aren't.
- Data stays in the browser after sign-out.
- The live site is deployed from an unprotected branch.
- The migration history has drifted from production.

## What's in good shape

| Area | Finding |
|---|---|
| Row-level security | On for all 10 public tables. Every policy is scoped to `auth.uid()`; project access goes through `private.is_project_owner()` / `is_project_member()`. |
| Write rights | Column-level grants limit what members can change. Projects: name, focus, tags, rung, tasks, workspace (never `owner_id`). Documents: title and body. Messages: body and recipient on insert, `read_at` on update. Connections: `status` only, and only by the addressee. |
| Earned fields | `protect_profile_stats` resets `sprint_rating` / `sprint_reviews` on any member write, so the verified work record can't be self-awarded. |
| Age | `check_member_age` refuses under-18 birth dates. Connection requests require both members to be adults (`is_adult_member`). |
| Sign-up | `check_signup()` runs inside Auth, so it fails closed. It requires Google only, a Google-verified email and no blocklist match, and invite-only is **on**. Even if the Email provider were switched on by mistake, password accounts would be refused. |
| Directory | `member_directory()` and `find_member()` return only the fields each viewer may see. They honour invisible mode, blocks and "connections only", and never return birth dates; CVs show only to connections. |
| Functions | Every `SECURITY DEFINER` function has `search_path = ''`. The advisor's three warnings (`find_member`, `member_directory`, `my_blocks` callable by signed-in members) are intended: they're how the directory works, with curated output. |
| Storage | `cvs`: private, 10 MB, PDF or Word only; readable by the owner and accepted connections. `avatars`: public by design, 2 MB, JPEG, PNG or WebP only, each member writes only their own folder. |
| Size limits | Constraints cap messages (2,000 characters), notes (300), documents (200,000), the workspace (256 KB), tasks (100), names, tags, links and preferences. |
| Realtime | Only `connections` and `messages` are published, and table RLS applies to those changes. |
| Browser | Content-Security-Policy on every page: scripts from this site only, with no inline script except one hashed line in the 404 page. Images only from this site, Supabase and Google profile photos; connections only to Supabase. |
| Member content | Document HTML is cleaned when it's shown as well as when it's saved (allowlist of tags; links `https:`/`mailto:` only). Member links go through `safeUrl()`. A hostile-text test runs in CI. |
| Secrets | Only the public anon key is in the repo; no service-role key anywhere in the git history. CI has read-only permissions. |
| Dependencies | `npm audit`: 0 vulnerabilities. The browser bundle is a pinned, vendored supabase-js 2.58.0. |
| Advisors | Performance: none. Security: the 3 intended warnings above, plus leaked-password protection (below). |

## Findings

Severity is for this prototype's situation: invite-only, a small trusted cohort.

### Medium

1. **Saves after removal or deletion look successful.**
   - **What happens:** when a co-founder has been removed, or the project deleted, saves resolve as if they worked. RLS keeps the data out of the database, but nothing tells the user.
   - **Where:** `db.changeColumn` returns `null` and callers treat it as success (`db.js:447`, `workspace.js:110`, `state.js:657`).
   - **Fix:** Gate 1 → 3 (E2E-04, E2E-09).
2. **Sign-out leaves workspaces and document text in localStorage**
   (`state.js:829`; keys `mori.<uid>.ws.*` and `mori.<uid>.docs.*`).
   - **Risk:** on a shared or campus computer, the next person can read them.
   - **Fix:** a one-line change to clear those keys too. Ready to do as a small separate PR on your go-ahead.
3. **The live site deploys from an unprotected branch.**
   - **What happens:** GitHub Pages builds from `claude/festive-allen-tw9q27`. Anyone with push access to that branch changes production immediately, with no review or CI gate. `main` is two releases behind what's live.
   - **Fix:** after merging, switch Pages to build from `main`, and turn on branch protection there (Checks, plus E2E staging once it exists).
4. **Migration history drift.**
   - **What happens:** production's applied versions (e.g. `20261115142305_invite_only_signup`, one combined `20261116151941_…`) don't match the files in `supabase/migrations/` (e.g. `20261114160000_…`, three separate files from 16 Nov).
   - **Risk:** a `supabase db push` against production would try to re-apply migrations. Staging is unaffected, since it starts empty.
   - **Fix:** align them with `supabase migration repair` or by renaming the files, with your approval. CLAUDE.md now forbids pushing to production meanwhile.
5. **No backups on the Free plan.**
   - **Risk:** a bad migration or a mistaken delete can't be undone.
   - **Fix:** decision D-05 (Pro, before the pilot); daily backups come with Pro.

### Low

6. **The site can be framed by other sites (clickjacking).**
   - **Why:** GitHub Pages can't send `X-Frame-Options`, and `frame-ancestors` doesn't work in a `<meta>` policy.
   - **Fix:** a few lines of frame-busting script, or later a CDN in front of Pages that can set headers.
7. **The signed-out `anon` role holds full rights on `profiles`.**
   - **Current state:** RLS blocks it, since no policy allows anon.
   - **Fix (defence in depth):** `revoke all on public.profiles from anon`.
8. **Profile text has no server-side limits.** `bio`, `headline`, names, skills and languages are unlimited, and `avatar_url` has no `https:` check.
   - **Risk:** layout or storage abuse; the security policy already blocks images from other hosts.
   - **Fix:** add check constraints like the ones the other tables have.
9. **Members can rewrite their own `created_at`** (shown as "Joined …") and `age`.
   - **Effect:** cosmetic, but it's a trust signal on profiles.
   - **Fix:** take those columns out of the update grant.
10. **Leaked-password protection is off** (advisor).
    - **Why it's low:** it only matters for password sign-in, which production refuses. Turn it on if the plan allows.
11. **No rate limits beyond Supabase's defaults** on connection requests, reports and messages. The invite-only cohort keeps this low for now.
12. **The Supabase session lives in localStorage.** That's standard for a static site; the strict CSP is the mitigation.
